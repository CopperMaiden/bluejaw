# Week 1 (Estimated ~12 hours)

With the initial design concept in mind, I took to wikipedia to research the bluetooth protocol, [found here](https://en.wikipedia.org/wiki/Bluetooth). I learned that there would need to be multiple devices with a bluetooth implementation in order for there to be multiple outputs for audio sharing. That limitation lead me to search through the electronics component distributing company, Digikey. 

In my mind, the design would center around, initially, only 3 bluetooth capable modules, which would all be made portable via a rechargeable battery. For a small, portable device, the bluetooth modules needed to meet the following criteria: 
- Energy efficient 
- Reliable 
- Tiny
- Built in microcontroller (to handle peripherals and peer communication)
- Low cost

With all of the criteria in mind, I ended up selecting the "ESP-32 C3 MINI 1 N4", a capable microcontroller with bluetooth and wifi, all in an SMD package that could interface with a PCB nicely.
![MFG_ESP32-C3-MINI-1](https://blueprint.hackclub.com/user-attachments/blobs/proxy/eyJfcmFpbHMiOnsiZGF0YSI6MTAyMzEyLCJwdXIiOiJibG9iX2lkIn19--9f93df52c83e2f58d68361db6377d55161a556a1/MFG_ESP32-C3-MINI-1.jpg)

The ESP-32 C3 draws between 290mA ~ 350mA at the most, and since there was only 3 of them (at the time), I assumed the maximum draw of current from the battery would be 1050mA, give or take. With a selected PCB size of 80mm by 50mm (about the size of an altoid's tin), the battery would need the following criteria:
- Smaller than 80mm (length) by 50mm (width)
- Near 3.3 Volts (For the ESP-32 C3)
- At least ~2 hours of battery life when running at full load

I decided on the MIKROE-1120, a 3.7 volt and 2Ah rechargeable lithium-ion battery (63.5mm x 44.2mm x 7.0mm).
![MFG_MIKROE-1120](https://blueprint.hackclub.com/user-attachments/blobs/proxy/eyJfcmFpbHMiOnsiZGF0YSI6MTAyMzE5LCJwdXIiOiJibG9iX2lkIn19--0ae6b7e29e327d8a18f5cdf8535f92e4346ad2d3/MFG_MIKROE-1120.jpg)

### Hardware to program the ESP-32 modules

I knew that at some point, I'd need to add a method to actually flash the firmware I write to the ESP-32 modules so they could function as intended. I landed on a 3 pin male header with 2.54mm pitch, the 61300311121 to be exact:

### Charging/Battery protection

A problem exists when both the USB-C receptacle and battery can actively provide power to the restof the circuits at the same time. To fix it, I added a transistor that would cut the battery off whenever power could be supplied from the USB-C port instead. Here's an image of the schematic with that implementation.
![Screenshot 2026-02-14 201413](https://blueprint.hackclub.com/user-attachments/blobs/proxy/eyJfcmFpbHMiOnsiZGF0YSI6MTA0NDc5LCJwdXIiOiJibG9iX2lkIn19--951289b9f7a3bf11a32e651fe3323ed0ad58eb06/Screenshot%202026-02-14%20201413.png)

But, as you may immediately notice, as did I a few minutes after adding the transistor, it would not function as intended at all. The way that the transistor is wired in this schematic achieves nothing, and only makes the problem worse. For context, the label marked "BAT" is the output that the rest of the circuit would use from the battery as power. If the transistor were implemented as shown in the schematic, it would prevent the battery from providing any power, and additionally have a useless gate that opens to nothing if power is added via the USB-C receptacle. Regardless, I knew I'd need a different cut-off solution, so I moved onto another part of the design to step away and give myself time to think. The transistor I used was the FMMT619TA, picture shown below.
![31~SOT23-3~F,N,SA~3](https://blueprint.hackclub.com/user-attachments/blobs/proxy/eyJfcmFpbHMiOnsiZGF0YSI6MTA0NDg3LCJwdXIiOiJibG9iX2lkIn19--ce8db714c332eedb4befaf491400f689b0577633/31~SOT23-3~F%2CN%2CSA~3.jpg)

To combat the difference between the battery's 3.7 volts and the USB-C receptacle's 5 volts, a linear regulator was added: an LD39200PU33R. The IC is capable of a 2A output at 3.3 volts, a perfect solution for the device's 3.3 volt requirement from the ESP-32 modules. Previous estimation of current draw from the ESP-32 modules was done with only three modules, but there are four. Current draw from four ESP-32 modules can be estimated with 350mA * 4 = 1400mA, which would be within the limits of the regulator. The 2A output of this linear regulator is not strictly enforced, but rather just a limit. The device would output a steady 3.3 volts for the ESP-32 modules with leeway for additional peripherals (like the display).

### ESP-32 peer to peer communication (communication between modules)

UART is a more than capable serial communication protocol for this project, with some minor modifications in firmware to give it multi-device capability. While it's slower than I2C or SPI, it works nicely with an IC that helps the USB-C receptacle communicate in UART, reducing the overall complexity I'd have to deal with if I used a different protocol, at least on the hardware side of things.

An early implementation of UART involved connecting each ESP-32 module to a single ESP-32 module that would act as the parent, however, as you will see in the image below, I initially connected all of the transmit and recieve lines together, until I could decide which module was the most ideal to select as the parent with additional components added to the board.

However, speed is not that important in this implementation, as the firmware of this device should merely interpret every connection as a signal to iterate through various menus.

Recall the ESP32-C3-MINI-1-N4 modules used for the only PCB in this project. Since these microcontrollers act as the heart of the device, controlling peripherals and making bluetooth audio sharing possible on a larger scale, the code will primarily revolve around designing firmware that achieves the necessary functions outlined in a previous journal entry.

![Screenshot 2026-02-15 123931](https://blueprint.hackclub.com/user-attachments/blobs/proxy/eyJfcmFpbHMiOnsiZGF0YSI6MTA1MDk5LCJwdXIiOiJibG9iX2lkIn19--e3f8ed44584f8c283d965786e95cc49e95788170/Screenshot%202026-02-15%20123931.png)

The four modules you see in the schematic above all have a unique quality to them. 
- B1: (Parent module) Has the responsiblity of controlling all child ESP-32 devices, as well as reading the rotary encoder, and using UART communication from the bridge IC to recieve firmware updates.
- B2: (Child module) Interpret or otherwise pass on the reading from the analog to digital converter attached to it's GPIO
- B3: (Child module) Control the display and update as instructed by the parent ESP-32 module
- B4: (Child module) No attached peripherals or additional responsibility

So, with four unique devices, a different set of instructions will be required of each device.

To program the microcontrollers, a slight alternative solution to regular UART connections is required, as the USB to UART bridge IC is only connected to B1, the parent ESP-32 module. I imagined using B1 as a messenger to flash the other three devices, since the capability of being able to individually address them could make it possible. I'd merely need to find a way to implement communication in firmware that allows the parent ESP-32 to act as a middle-man when flashing new updates to the four microcontrollers.

In PlatformIO, an embedded system development ecosystem, I was able to define different primary source files for each ESP32 module.

Note that the baud rate is defined here as well. I selected 9600 as the baud rate for both monitoring in the terminal and uploading, purely because I thought it'd be reliable, but I could definitely go faster, considering the USB to UART bridge IC's 3 megabaud limit.

(This explains how the chip is able to communicate with a device like a laptop so long as the laptop can also speak in "UART". The ESP32 and the laptop can "share" a language by both using UART, which they do, thanks to the USB to UART bridge I implemented previously on the PCB.)

- There are two onboard analog to digital converters from the ESP32, but luckily my manual implementation of an ADC is still necessary, since the documentation seems to imply there would be additional configuration required to make the onboard ADCs accurate in their readings.
